Findings
- ghostEngines/autograd_grad_sample_dotprod.py:25-66 `_NamedSavedTensorManager` stores the capture buffers (`captured`, `captured_all`, `used_ids`) in `threading.local()`. On CUDA, autograd executes backward hooks on worker threads, so the forward-side pack hook fills the main thread-local buffers, but the backward hook reads a different (empty) thread-local store. Repro: after a forward pass inside `engine.saved_tensors_context()` on GPU, `captured_all` contained 42 tensors and `output` had two captures; when the backward hook for `output` fired, `captured_all` and `captured['output']` were empty, triggering the runtime error seen in `run_train_with_ghost.sh`. This design works on CPU (single-threaded autograd) but fails on GPU where backward runs off-thread.
- ghostEngines/autograd_grad_sample_dotprod.py:43-65 The `used_ids` book-keeping is also thread-local, so even after fixing capture visibility, different autograd threads could re-use the same saved tensor for multiple layers because each thread sees its own empty set. This risks silent mis-association of activations when the engine is used in multi-threaded backward execution.

Patch plan
- Refactor `_NamedSavedTensorManager` to keep capture buffers (`captured`, `captured_all`, `used_ids`) in shared instance state (with a lightweight lock if needed) instead of `threading.local`, while keeping the forward-only scope stack thread-local. Reset the shared buffers in `enable/disable`.
- Ensure `resolve_activation` in backward reads the shared buffers and shared `used_ids`, so activations saved on the forward thread remain visible to autograd worker threads and are only consumed once across threads.
- Add a focused regression check (small CUDA forward+backward under `engine.saved_tensors_context` with autocast) to confirm `captured_all` is populated and `resolve_activation` succeeds for `output`, then re-run `./tests/torchtitan/run_train_with_ghost.sh` (or the minimal CUDA repro) to verify the hook no longer throws.
